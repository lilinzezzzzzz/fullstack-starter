# 已有项目架构对齐指南

本指南面向正在开发或已经运行的项目，说明如何参考本脚手架整理职责、依赖、配置与运行方式。目标是在业务持续可用的前提下逐步收敛架构；目录名称相同只是结果的一部分。

本文件维护通用方法，原项目自己的差异、决策、迁移批次和验证结果应保存在原项目中。当前脚手架的架构见[设计方案](design.md)，从零创建独立项目见[项目创建指南](project-creation.md)。

## 先确定对齐范围

先确认原项目的使用者、部署环境、并发与数据要求，再决定采用哪些约束。下表中的“单独评估”表示需要作出明确选择，而非迁移时自动改成脚手架的选型。

| 方面           | 可参考的组织原则                                      | 需要单独评估的选择                             |
| -------------- | ----------------------------------------------------- | ---------------------------------------------- |
| 业务分层       | HTTP 适配、业务规则、持久化模型与 I/O Schema 职责清楚 | 是否采用相同目录、是否已有必要的领域或模块边界 |
| 依赖与生命周期 | 在组装边界注入依赖，明确资源创建、共享范围和关闭责任  | 同步或异步访问、资源池、后台任务与 worker 模型 |
| 数据与维护     | 版本化迁移、事务边界、备份恢复和测试隔离              | 数据库类型、迁移工具、停机窗口与兼容期         |
| 配置           | 统一加载和校验，区分公开客户端值与私有服务端值        | TOML、环境变量、配置中心及已有部署注入机制     |
| 运行           | 启动入口明确，正常关闭与失败清理可验证                | 单 worker、单机、前台服务或现有进程与容器管理  |
| 前端与 API     | 请求边界集中、取消可传播、接口类型有可信来源          | React/Vite、UI 库、前端独立部署或由后端托管    |
| 可观测性       | 错误、日志与链路上下文有一致的关联方式                | Loguru、trace 协议迁移、采样、采集和导出策略   |

SQLite、本地单用户、全部必填 TOML、FastAPI 托管前端以及只维护 trace 上下文，是本脚手架的具体选择。原项目若有远程用户、多进程、既有数据库或采集需求，应保留满足这些需求的设计，并记录与参考架构的差异。

“只有 Hello 示例、没有业务表”仅约束脚手架。对齐已有项目时必须保留其业务能力、数据、迁移历史和必要基础设施。不要用创建脚本覆盖原项目，也不要整体复制本项目的 `AGENTS.md` 作为原项目的新规则。

## 1. 只读盘点与验证基线

在修改代码前，检查原项目的说明、指令、工作区改动及以下证据。先执行安全、可重复的本地检查；需要真实服务、凭据或生产数据的部分明确列为待验证，不通过试运行生产操作补齐盘点。

| 盘点项       | 应记录的内容                                                  |
| ------------ | ------------------------------------------------------------- |
| 入口和调用链 | HTTP、CLI、任务、事件等入口，以及到持久化或外部调用的完整路径 |
| 对外契约     | 路径、请求/响应、错误码、客户端类型、任务消息与外部使用方     |
| 数据         | 数据库类型、模型注册、会话/事务边界、迁移版本、备份恢复方式   |
| 配置和运行   | 配置来源、路径规则、启动参数、部署方式、信号与关闭流程        |
| 依赖和资源   | 数据库连接、HTTP 客户端、缓存等由谁创建、共享和关闭           |
| 前端         | 路由、请求封装、状态管理、构建注入、托管与代理关系            |
| 验证能力     | 可运行命令、关键业务场景、已有失败、环境限制与测试数据位置    |

给基线记录日期、代码 ref 或差异范围、命令、结果和未验证项。至少选出一条能重复验证的关键业务流程，覆盖输入、核心规则、持久化或外部副作用及失败行为；缺少自动化测试时，先为准备迁移的行为建立必要回归用例。

验证数据和服务必须属于本次验证。不要为了建立基线连接日常库、重置共享数据、终止已有服务或改写线上配置。

## 2. 建立职责差异表

逐项填写原项目的真实位置与证据，然后选择保留、移动、拆分或暂缓。已有清晰的模块边界可以继续使用，不为目录一致引入额外抽象。

| 职责                          | 本脚手架的参考位置                                     | 检查重点                                               |
| ----------------------------- | ------------------------------------------------------ | ------------------------------------------------------ |
| HTTP 参数、依赖声明和响应映射 | `backend/app/routers/`                                 | 业务规则、写事务是否混入请求适配                       |
| 业务规则和事务                | `backend/app/services/`                                | 业务类是否处理 Request、构造 I/O Schema 或创建基础设施 |
| 持久化结构与接口 Schema       | `backend/app/models/`、`backend/app/schemas/`          | ORM 与接口结构是否耦合，模型是否完整注册               |
| 依赖组装                      | 各 Service 模块的 `new_*_service` 工厂                 | 构造注入、请求作用域与 CLI 组装是否明确                |
| 应用与资源生命周期            | `backend/app/main.py`、`backend/app/database.py`       | 导入副作用、启动检查、失败清理和关闭责任               |
| 维护与迁移                    | `backend/app/maintenance/`、`backend/migrations/`      | 请求路径是否执行维护，迁移是否隐式运行                 |
| 运行入口与工程工具            | `entrypoints/`、`scripts/`、`backend/tools/`           | 工具与应用依赖方向、运行方式和失败退出                 |
| 前端请求、查询与呈现          | `frontend/src/api/`、`hooks/`、`pages/`、`components/` | 请求取消、重试、状态与呈现是否职责清楚                 |
| 文档与协作规则                | README、`docs/`、分层 `AGENTS.md`                      | 当前状态、目标状态和历史证据是否分开                   |

原项目可使用以下表头记录决策；证据填写具体文件、符号、调用方或检查结果，不仅写目录名：

| 职责   | 当前实现与证据 | 目标与保留差异 | 处理方式                  | 影响的调用方 | 验证与回退 |
| ------ | -------------- | -------------- | ------------------------- | ------------ | ---------- |
| 待填写 | 待填写         | 待填写         | 保留 / 移动 / 拆分 / 暂缓 | 待填写       | 待填写     |

## 3. 试迁一条业务链路

选择影响范围可控、又包含真实业务规则的链路，优先包含事务或外部调用，避免仅用健康检查验证方案。

1. 固定这条链路的现有契约与回归用例，包括成功、失败、边界值，以及实际存在的事务回滚或取消行为。
2. 先整理职责：请求适配留在 Router，业务规则与写事务放入 Service，响应 Schema 在边界映射；保持现有领域边界。
3. 在工厂或其他明确的组装边界注入依赖，业务类不自行读取请求上下文或创建连接。资源的共享范围和关闭责任不能因移动文件而改变。
4. 核对全部调用方，包括 HTTP、CLI、任务和测试；验证导入、注册、启动与原有业务流程。
5. 审查实际 diff，确认没有夹带接口改版、数据转换或依赖升级，再决定是否将此链路作为后续样板。

若原项目使用同步数据访问，试点阶段可先保留同步实现。异步化需要独立评估会话、事务、取消和连接关闭，不应仅因目标目录使用 async 而一并切换。

## 4. 按独立批次扩大范围

按依赖关系确定顺序，每批只有一个可解释的目标。下面是建议拆分，不代表每个项目都必须执行全部批次：

| 批次               | 主要工作                                     | 验证重点                                     |
| ------------------ | -------------------------------------------- | -------------------------------------------- |
| 职责整理           | 先迁试点，再逐个业务模块整理分层、导入和注册 | 业务结果、所有入口与接口契约保持兼容         |
| 资源与生命周期     | 收敛连接和客户端的构造、注入、启动与关闭     | 启动失败、异常、取消和正常关闭都释放资源     |
| 配置               | 统一校验、路径解析和公开白名单               | 既有部署输入的迁移方式、缺项失败与私有值隔离 |
| 数据访问或迁移机制 | 分别安排异步化、事务调整或迁移工具变化       | 旧数据、实际前序版本、约束、回滚和并发边界   |
| API 与可观测性     | 分别调整错误契约、接口类型、日志和 trace     | 客户端兼容、链路关联、失败行为与敏感信息     |
| 构建和运行方式     | 按需调整前端托管、启动入口或部署流程         | 构建注入、真实启停、访问路径与部署兼容性     |
| 文档和指令         | 每批同步当前设计、命令与局部规则             | 说明准确，未完成目标不写成已经生效的约束     |

配置切换、数据库变更、API 协议变化与服务部署可能需要兼容期。批次计划应明确先部署哪个兼容版本、旧调用方何时退出，以及什么条件下才能收紧约束；只有确认没有兼容需求时才直接切换。

数据库类型切换、依赖大版本升级、UI 框架替换和新业务功能属于各自的变更，应另行安排。可以与架构对齐建立依赖关系，但不要混入文件移动批次。

## 5. 每批验收与回退

每批开始前记录目标、边界、调用方、数据影响、验证命令和失败后的处理方式；完成后逐项对照：

- 业务行为与对外契约符合基线或已明确接受的变更，调用方和生成类型同步。
- 定向回归通过；按实际影响补充集成、构建、真实启停或页面验证。未运行项目列明原因，历史通过不代替当前结果。
- 资源所有权、事务与取消边界明确，不产生额外导入副作用、连接泄漏或不受控的后台任务。
- 配置、运行路径、私有信息和测试数据边界保持有效；运行方式变化已有对应环境证据。
- diff 中没有无关改动，文档描述实际状态，剩余差异与风险有明确归属。

代码组织调整通常可通过版本控制回退，仍需核对配置与调用方兼容性。数据转换不能依赖代码回退恢复：需要在执行前验证可恢复的快照、旧数据升级路径与恢复步骤；仅在 schema 层降级并不证明数据可还原。生产或外部变更按原项目的授权流程执行。

## 在原项目中落地计划

在原项目保存一份架构对齐计划，引用本指南并记录实际适配结果。计划至少包含：

- 盘点基线、采用的参考版本，以及保留的数据库、部署和业务特性。
- 职责差异表与明确选择，尤其是没有采用脚手架约束的原因。
- 各批次目标、依赖顺序、修改范围、契约与数据影响、验收和回退条件。
- 已执行的验证、未解决问题和剩余工作；只有有证据完成的批次才能标为完成。

README 继续负责原项目的使用入口，设计文档描述已落地架构，计划管理尚未完成的迁移，历史文档保留实测证据。`AGENTS.md` 仅写已经采用的协作与架构约束，并按实际目录分层维护。

完成对齐的依据是职责、依赖、资源和契约满足原项目已选定的目标，且有对应验证证据；保留有理由的架构差异是允许的，不要求复制所有目录与技术选择。
